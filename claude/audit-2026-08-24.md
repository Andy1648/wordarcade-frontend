# Codebase Audit — 2026-08-24 (branch `audit/2026-08`)

## Read-cold summary (10 lines)
1. **No HIGH-severity findings survived refutation.** The new XP/Wins/Shop layer is
   defensively coded: every localStorage access is wrapped, and progression state cannot be
   *corrupted* by a game-mode failure (worst case is a missed or double-counted payout — an
   inflation, not corruption).
2. **Area 2 (localStorage) is clean** — all 16 read/write sites across the app have try/catch
   + sane defaults, including bare `window.localStorage` property access (which itself can throw
   in locked-down Safari). Nothing to fix.
3. **Your decision needed on:** (a) the `WordCountChip` component — it's fully built but wired
   into nothing (dead file); keep for later or cut? (b) the ~24 always-on menu card-art infinite
   animations — intended "personality" or a battery cost worth gating?
4. **Top MED fixes:** Homepage's scroll handler reads layout for every card on every scroll
   event (unthrottled); the Shop/Stats overlays have no Esc-to-close and don't move focus into
   themselves on open.
5. **The project doc's "1 infinite animation" claim is wrong:** there are **96** `infinite`
   declarations; only **4** are gated by `animation-play-state`; ~58 `prefers-reduced-motion`
   overrides gate most for RM users, so a *default* user runs essentially all 96 continuously.
6. **What I did NOT check:** runtime/2-device live play (read-only audit, no app run); the
   backend; `src/solo/**` (owned by another branch, excluded per instructions); exhaustive
   orphaned-CSS-class enumeration (I spot-checked, did not diff every selector against usage);
   and I did not measure actual animation GPU cost, only counted declarations.

Severity legend: **HIGH** = can break prod / lose or corrupt data · **MED** = degraded UX,
perf, or a11y · **LOW** = cleanup / polish. Every finding is read-only; nothing was changed.

## Area 1 — XP/Wins/Shop coupling to game-mode code

**Verdict: the layer is loosely coupled and a mode failure cannot corrupt progression state.**

Couplings (each is a one-way call from mode code into the progression model; the model never
calls back into a mode):

| Site | Call | Trigger |
|---|---|---|
| `App.jsx:998` | `recordRound({mode:'blitz', wordsAccepted: myBlitzAcceptedRef})` | Blitz `round_end` |
| `App.jsx:1023` | `recordRound({mode:'wordBomb', wordsAccepted: myWbAcceptedRef})` | Word Bomb `game_over` |
| `satRush/SatRushGame.jsx:48` | `recordRound({mode:'satRush', wordsAccepted: results.cleared})` | SAT Rush results |
| `App.jsx:985` / `888` | `myBlitzAcceptedRef++` / `myWbAcceptedRef++` | each accepted answer |
| `useXpCapture.js:65` | `creditXp` (menu typing only) | menu/splash keystroke/tap |

- **Corruption is not possible.** Every write goes through the wrapped setters in
  `xp.js` / `wins.js` / `shop.js`, each of which serialises one key as a string or JSON. A mode
  crash mid-round simply means `recordRound` is never reached → no payout. There is no
  read-modify-write across keys that a partial failure could leave inconsistent. (`recordRound`
  at `wins.js:88` does `getWins()+granted` then `saveWins`, but a throw is swallowed inside the
  wrapped setter, so the balance is either updated or left as-is — never half-written.)
- The accept-count refs are reset at the right lifecycle points: `myWbAcceptedRef` on
  `game_started` (`App.jsx:752`), `myBlitzAcceptedRef` on `round_start` (`App.jsx:955`).

**Finding 1.1 (LOW, uncertain) — duplicate `round_end`/`game_over` would double-pay.**
`App.jsx:998,1023`. Because the FIFO drain processes every queued frame, two `round_end`
frames for the same round (a server resend, or a duplicated frame) would call `recordRound`
twice against the same un-reset accept count, paying wins twice and bumping the round counter
twice. This is server-controlled (a reconnect can't cause it — the app blocks reconnect during
a live game, `useWebSocket.js`/`canReconnectRef`), so it requires a server bug to manifest.
*Smallest fix:* guard with a per-round "already paid" ref keyed on the round/game id, cleared on
`round_start`/`game_started`. I flag this LOW and note the uncertainty: I could not find a
client path that emits a duplicate, so it may be purely theoretical.

**Finding 1.2 (LOW) — the game-mode XP multipliers are dead in production.**
`xp.js:13-18` defines `XP_MULTIPLIERS['word-bomb'|'category-blitz'|'sat-rush']` (20/20/30) and
`xpPerInput` accepts a `mode`, but the only non-test caller is `useXpCapture.js:46` with
`mode:'menu'`. Game modes award **wins**, never XP. So those three entries and the `mode`
parameter are exercised only by `xp.test.js`. Not a bug — likely staged for a future
in-game-XP feature — but currently dead. *Fix:* leave as-is if the feature is planned; otherwise
drop the unused entries.

## Area 2 — localStorage safety

**Verdict: clean. No findings.** Every access is wrapped with a sane default:

| Module | Sites | Default on failure |
|---|---|---|
| `progress/xp.js` | 58,68,175,190-191,201,211 | 0 / no-op |
| `progress/wins.js` | 17,27,50,64 | 0 / `{}` zeroed |
| `progress/shop.js` | 44,54,67,78 | defaults array/loadout |
| `progress/clack.js` | 37,47 | enabled=true |
| `daily/streak.js` | 116,126 (bare `window.localStorage`) | `emptyDailyState()` |
| `playerName.js` | 36,48 | '' / in-memory |

| `wordCount.js`, `visitHistory.js`, `satRush/recentWords.js`, `solo/shared.js`, `satRush/useSatRushGame.js:41` | — | 0 / null, all wrapped |

- Safari private mode / quota-full: the failure surface is `setItem` throwing and the
  *property access* `window.localStorage` throwing (sandboxed contexts). Both are covered —
  `streak.js:116` reads `window.localStorage` *inside* the try, and `useSatRushGame.js:36-41`
  explicitly guards the property read. Reads that return `null` (private mode getItem) are
  handled by the `raw == null` / `!raw` checks everywhere.
- Minor robustness note (not a finding): `GameScreen.jsx:93-94` does `JSON.parse(raw)` then
  `parsed.score`; if a hand-edited value stores JSON `null`, `parsed.score` throws — but it's
  inside the try/catch, so it degrades to `null` correctly.

## Area 3 — Unhandled states

- **Error boundary: present but single.** `main.jsx:81` wraps `<App/>` in
  `Sentry.ErrorBoundary` with an on-brand `CrashFallback` (reload button). *Finding 3.1 (LOW):*
  it is the only boundary, so a render throw inside the Shop/Stats overlay (or any screen) tears
  the whole app down to the reload screen rather than isolating the overlay. *Fix:* wrap the
  lazy `{screen}` (`App.jsx:1792`) — or just the overlay routes — in a nested boundary that
  returns to the menu.
- **Lazy-chunk safety:** all lazy screens (Shop/Stats/Game/etc.) are covered by one
  `<Suspense fallback={null}>` at `App.jsx:1792` — no missing-Suspense throw.
- **WS disconnect mid-round: handled well.** `useWebSocket.js` blocks reconnect while
  `canReconnectRef.current === false` (active room/game), because the backend treats a
  reconnect as a fresh player with no resume; it surfaces `closed`/`error` for the UI instead of
  silently resurrecting a dead seat. Stale-socket events are ignored via `isCurrent()`
  (`:105`). Malformed frames are caught at `:121`.
- **Round ending while an overlay is open:** Shop/Stats are *view swaps* (`App.jsx:1657-1660`),
  not layers over a live game — they are unreachable during `view==='game'`, so "round ends
  while shop is open" cannot occur for them. The genuine in-game overlays (results, toast) are
  driven by the same drain and are state-swapped on `round_end`/`game_over`. No finding.
- **Promise rejections:** no unguarded top-level `.then()` without `.catch` found in the new
  layer; the model modules are synchronous. (I did not audit every async path in GameScreen's
  in-game logic — out of the new-layer scope.)

## Area 5 — Layout reads in per-frame / per-keystroke paths

**Finding 5.1 (MED) — Homepage scroll handler reads layout for every card on every scroll
event.** `Homepage.jsx:229` attaches `updateState` to the menu's `scroll` (passive but
**unthrottled**). `updateState` (`:210-219`) calls `getBoundingClientRect()` on the region and
on *every* `.game-card-magnet`, plus `scrollHeight`/`clientHeight`/`scrollTop`. On mobile
momentum scroll, scroll events approach one-per-frame, so this forces a full layout read of all
cards each frame while scrolling the menu. *Smallest fix:* coalesce with rAF — set a
`ticking` flag, do the reads once per frame:
`onScroll = () => { if (!ticking) { ticking = true; requestAnimationFrame(() => { updateState(); ticking = false; }); } }`.

**Finding 5.2 (LOW) — `magneticPull.frame()` reads `getBoundingClientRect()` per element per
rAF frame.** `lib/magneticPull.js:86`, inside the shared rAF that runs while the cursor is
engaged. *Refuted down from MED:* the hook only registers on
`(hover: hover) and (pointer: fine)` and not reduced-motion (`:162-164`), so it **never runs on
touch/mobile**, only a handful of elements register, and the loop stops at rest (`:131-132`).
Bounded desktop-only cost. *Optional fix:* cache each element's untransformed rect on
register + a scroll/resize listener (as `GameCard.jsx:45` already does) to drop the per-frame
read.

**Not a finding:** the per-**keystroke** menu path (`useXpCapture` → `MenuXpFx.letterPop`) does
**no** layout read — spawn slots and the bar box are measured on mount/resize and cached
(`MenuXp.jsx` measure effect). `writeFrame`'s `clientWidth` read (`:54`) is a one-time
cache-miss fallback, not per-frame.

## Area 6 — Accessibility (new overlays)

**Finding 6.1 (MED) — Shop & Stats overlays: no Esc-to-close and focus is not moved into the
overlay on open.** `ShopScreen.jsx:72` / `StatsScreen.jsx:52` set `role="dialog"` +
`aria-label`, but: (a) there is no `keydown`/Escape handler — the only close paths are clicking
✕ or BACK; (b) on open, focus is not programmatically moved into the panel, and since the
homepage unmounts on the view swap, focus falls to `document.body` — a keyboard/SR user must Tab
from the top to reach the controls; (c) no `aria-modal="true"`. *Mitigating:* every control is a
real `<button>` (reachable/operable), and because these are full-screen route swaps there is no
live content behind them to trap focus against — so a full focus-trap is not strictly required.
*Smallest fix:* add an Escape handler calling `onBack`, and focus the ✕ (or panel) in a mount
effect.

**Finding 6.2 (LOW) — the XP bar is `aria-hidden="true"`** (`MenuXp.jsx:111`), so level/XP
progress is invisible to assistive tech. This looks deliberate (it's decorative chrome and the
readout duplicates in Stats), but note that a screen-reader user gets no progression feedback on
the menu. The pop/level-up FX layer is also `aria-hidden` (correct — pure decoration).

**Finding 6.3 (LOW / refuted contrast) — the "yellow-on-teal" combo the brief worried about is
not actually present.** I checked the new elements: teal (`#2effe0`) backgrounds always carry
**dark** text `#0d0618` (`ShopScreen.css:229-230`, `StatsScreen.css:112-113`, ~13:1 — excellent);
yellow (`#ffe94a`) is only ever text on the **dark** panel (`shop-card-mult` `:112-115`) or the
dark-on-yellow buttons (`:139-140`). No low-contrast yellow-on-teal pairing exists in the new
layer. (Small type: `shop-card-mult` is 11px — legible, adequate contrast.) Keyboard
reachability of the menu's SHOP/STATS entry points: they are `<button>`s in the homepage footer
(reachable).

## Area 7 — Infinite CSS animations (doc says 1; it's wrong)

**Finding 7.1 (MED, doc correction) — there are 96 `infinite` animation declarations, not 1.**
Counts (grep over `src/**/*.css`):

- **96** `infinite` declarations total. Heaviest files: `GameScreen.css` (37, in-game — only
  mounted during a match, acceptable), `GameCardArt.css` (**24**, the menu card mascot art),
  `SplashScreen.css` (8), `TransitionIntro.css` (5), `RoomScreen.css` (5).
- **Only 4** `animation-play-state` occurrences — so **only ~4 animations are pause-gated**; the
  rest run for as long as their element is mounted.
- **58** `prefers-reduced-motion` overrides gate most of them **for reduced-motion users only**.
  A default user (no RM preference) runs essentially all 96 continuously.

**The load-bearing one for the menu:** ~24 infinite loops in `GameCardArt.css` animate the menu
cards' mascot art whenever the homepage is mounted, gated only by reduced-motion. This is the
project's "nothing static" personality by design (the menu-xp e2e even relies on card-art loops
being RM-gated), but it *is* continuous GPU/compositor work on the idle menu for the majority of
users — worth a conscious decision. *Options:* gate the card-art loops behind
`animation-play-state: paused` unless hovered/`data-beat`, or accept as intended. Note this does
**not** contradict the "MENU MOTION LAW" doc (which removed *Homepage.css* idle loops — the
card-art lives in `GameCardArt.css` and was never in scope of that law). *Action:* update the
CLAUDE.md line that claims "1" to reflect ~96 / 4-gated.

## Area 8 — Mobile (`<=760px`) layout

The `<=760px` breakpoint appears in only two files: `Homepage.css` and `GameScreen.css`
(`grep` over `src/**/*.css`). The Shop/Stats overlays have **no** 760px block — they rely on a
fluid `dvh` panel with internal scroll (`StatsScreen.jsx:3` comment: "Scrolls internally… never
breaks 100dvh").

- **XP bar / pops on mobile: safe.** `.menu-xp-fx` is `position:absolute` + `overflow:hidden` +
  `pointer-events:none` (`MenuXp.css:121-125`), so pops are **clipped to the fx layer** and can
  never extend the scroll height of the menu container or intercept taps. Placement is inset by
  `POP_HALF` within the measured layer, so nothing spawns past the clip. No finding.
- **Overlays on mobile: safe.** Shop/Stats are full-viewport route swaps with an internally
  scrolling body and a fixed BACK button; they replace (not overlay) the scrolling menu
  container, so they don't inherit the menu's scroll quirks.
- **Homepage mobile:** `Homepage.jsx:188` switches on `matchMedia('(max-width: 760px)')` and
  computes `--rowh` + fold flags. The correctness is fine; the only concern is the scroll-read
  cost in **Finding 5.1**, which is most impactful exactly here (mobile momentum scroll of the
  card grid).

No mobile-specific breakage found beyond the perf note folded into 5.1.

## Refutation pass (high-severity candidates stress-tested)

The brief asks to refute every HIGH finding before it ships. After review, **no finding rose to
HIGH** — the progression layer's wrapped storage and one-way coupling rule out data loss/
corruption, which is what HIGH would require here. I additionally stress-tested the strongest
candidates:

- *"magneticPull per-frame layout read will jank mobile menu scroll"* → **refuted / downgraded to
  LOW.** The hook is gated to fine-pointer + hover and never registers on touch devices
  (`magneticPull.js:162`), so it contributes zero cost on mobile. Desktop cost is a handful of
  elements that settle to rest.
- *"a mode crash corrupts XP/wins"* → **refuted.** All writes are single-key, wrapped, and
  atomic-per-setter; a crash yields a missed payout, not a torn write.
- *"duplicate round_end double-pays"* (1.1) → **kept but LOW**, because I could not exhibit a
  client path that emits a duplicate (reconnect is blocked during a game), so it depends on a
  server-side resend I can't prove exists from this repo.
- *"yellow-on-teal fails contrast"* (6.3) → **refuted.** The combination doesn't exist; teal
  carries dark text, yellow sits on dark.
